Not here

  • Ask for consent. It asks here anyway. The spec says a server should, and the one recorded did every time, with that setting off and on.
  • Client type. Recorded with no secret, because software on someone’s own device generally cannot keep one. An app that had one would send it each time as well.
  • PKCE. The code that gets the tokens goes straight to the app and never through a browser, so the theft PKCE is for does not happen here. RFC 8628 does not include it.
  • An attacker. The code that gets the tokens never goes through a browser, so that theft is not here. What can go wrong here is under "Someone misusing it". The page that asks the user to agree is where someone can still stop that one.
  • External IdP. Only recorded on the authorization code flow so far.
  • A second app. Only recorded on the authorization code flow so far.
  • When the token runs out. Only recorded on the authorization code flow so far.
  • Log out. Only recorded on the authorization code flow so far.
  • What the API is sent. Only recorded on the authorization code flow so far.
  • Token type. Not recorded on this flow so far.
  • Server requires a nonce. Only drawn on the authorization code flow so far, from the RFC.

What other answers can there be?

If it asks too fast, the answer can be , and the app then has to wait 5 seconds longer from then on. That and this answer are the only two that mean carry on.
