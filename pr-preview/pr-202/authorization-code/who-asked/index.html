Someone registers it by hand, it registers itself, or it points at a document about itself. It changes the setup, and with a document the login too.

What the API is sent

The same call to the API, and what it answers depending on the token.

The API needs a second API to answer, and trades the token it got for one meant for that API.

What the trade gives back

Only a token for the second API, or a refresh token as well, so that the API can get another later without the user.

Drawn so far only on the plain flow, for an app with a secret and nothing else on.

Logged in, the user links an account at another provider, whose tokens the identity provider can keep.

Later on the access token expires, and the app gets a new one without the user.

A second app, the same identity provider, and no password.

The user logs out, and what ends is not everything.

Where the app runs

On a server of its own, in the page in the user’s browser, alone or with a server behind it, or in a program on the user’s computer. In the page alone there is nowhere to keep a secret, and in a program a secret shipped in every copy is no secret.

Which spec says so?

In Keycloak: Client scopes

The first API’s client has a client scope with an Audience mapper that names the second API, as a default scope. Without it, asking for that audience gets a 400 and: Requested audience not available: demo-api-two. With it, the new token names the second API, and not the first.
