Authlines

Flip one thing. Watch the login change.

You have probably clicked a button like “Log in with Google”. A button like that can keep your password from the app. Here is why that matters, and how, one message at a time.

  1. Start here

    8 What everything else builds on, in plain words.
    1. Why not just give the app my password? What came before, and what most of this is for.
    2. What is an identity provider, and an issuer? The place you log in, and how everything else knows which one it is.
    3. What is a token? What the app gets instead of your password.
    4. How does an app get access? An app acts for a user, without ever seeing their password.
    5. Why not just send the token back through the browser? Why the browser only gets a code, and what happened to the way that did not.
    6. What can the browser see? The whole flow with everything the browser was not sent hidden.
    7. How does an app know who logged in? Access is not identity, which is what OpenID Connect adds. OAuth alone is not login.
    1. I have to add login to an app. What do I do? The part you do once, which part of your code is left, and what a library does. An app with no browser takes the device flow.

  2. When something goes wrong

    7 An error on your screen, and what it means.
    1. Why do I get Invalid parameter: redirect_uri? Where the address is checked, and where it was registered.
    2. Why did my API say 401? It does not accept the token, for one of several reasons that look the same.
    3. What is the difference between 401 and 403? One is about the token, and the other about what it allows.
    4. What if someone changes what a token says? Anyone can read one, and nobody else can sign it.
    5. Why does my API refuse a token that is still good? It has to be for this API, which takes setting up at the identity provider.
    1. Why do I get login_required? Someone would have to log in, and the server was told not to ask.
    2. Why do I get Maximum allowed refresh token reuse exceeded? A refresh token was used twice, and that ended things for this app.

  3. Keeping it safe

    12 What can go wrong, and what stops it.
    1. What does state protect against? Cross-site request forgery, or CSRF: someone slipping their own answer into your login.
    2. What is iss doing in the address? Advanced It says which server answered.
    1. What is different about an app with no secret? An app in a browser or on a phone cannot keep one, so what proves who it is?
    2. What is the implicit flow? The token sent back in the address, and why current advice says not to.
    3. What if someone steals the code? From an app with no secret: watch them take it as it crosses the browser, and get the tokens.
    4. How does PKCE work? The app proves it started this login, with a value that was never in a redirect.
    5. Why not just put * in the redirect URIs? Advanced A login link someone else made, and the code going where it says.
    1. Does an app with a secret need PKCE too? Why current advice recommends it, even when a stolen code is not enough alone.
    1. What stops them handing it to the real app? The code is tied to the login it came from.
    1. What is a stolen refresh token worth? More than the access token, and a new one coming back may not stop it.
    2. How do I make refresh tokens rotate? Advanced A new one coming back is not enough: the old one has to stop working.
    3. How does DPoP stop a stolen token being used? Advanced Only where the API checks the proof. The theft itself is not drawn.

  4. Logging in somewhere else

    6 When the identity provider hands the login to another one.
    1. What if our users are already in LDAP or Active Directory? Advanced Same app, same token, a different middle.
    2. How do you log in with another provider? The app does not notice, and that is the point. It is one way "log in with your company account" works.
    3. How do we offer log in with your company account? Your provider finds their company from the email, and the app still knows only one.
    4. What if a customer's provider speaks SAML? Advanced Only the part between the two providers changes.
    5. What happens when someone leaves the customer's company? Advanced The token, a refresh and a login still work, while the session in the middle lasts.
    6. How does the app call the other provider's API? Advanced The identity provider kept its tokens, and hands them over.

  5. Setting up a real app

    12 The combinations people use, with what is really sent.
    1. Can an app register itself? Advanced An admin still hands over a token, and one request does the rest.
    2. What if nobody registers the app at all? Advanced A document at an address the app controls, fetched when it first asks.
    3. When does the user get asked? What a scope is, and why you may never have seen the question.
    4. What is single sign-on? Why don't I log in twice? A second app, the same login, and no password.
    5. How do an app and a provider get to know each other? What people have to do before anyone can log in.
    6. What does my API have to check? A token says nothing until someone has looked.
    7. What happens when the token runs out? The app gets a new one, and the user never knows.
    1. I logged out. Does the token still work? The same token, and two answers.
    2. Am I logged out of my other apps too? They lose the session they relied on, and may not know yet.
    1. Where should an app in the browser keep its tokens? localStorage, sessionStorage or memory: none of them fully stops a script in the page. A backend for frontend keeps tokens out of it, though a script can still send requests through it.
    2. What does a server behind the page change? The page never has a token, and the browser gets a cookie.
    3. What if our client secret is in the JavaScript? Then it is not a secret, and anyone can read it.

  7. When there is no user

    1 Client credentials: one service calling another, with nobody logging in.
    1. What if no user is involved? A nightly job, or one service calling another: machine to machine, with no browser and no login.

  8. On a TV, or a server with no browser

    5 Device flow: when the app cannot log anyone in, and the user does that on another device.
    1. How do you log in on a TV, or on a server with no browser? On another device, with a code the app shows. That includes a command-line tool over SSH on a headless server.
    2. Why are there two codes? One for a person, and one that gets the tokens.
    3. What is the app doing while the user types? Asking, again and again, which is called polling.
    4. Can someone trick me into approving their device? Yes, by sending you their code. It is called device code phishing.
    5. What if someone else can see the user code on the screen? They can get there first, and the device ends up logged in as them.
