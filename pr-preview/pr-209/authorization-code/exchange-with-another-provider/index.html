Can an API trade a token from a login at another provider?

Authorization code flow. Based on RFC 6749, RFC 6750, RFC 8693. Recorded from Keycloak 26.8.1 on 2026-11-05.

Settings

Adds proof of who logged in on top of the access OAuth grants.

The identity provider asks the user whether the app may have this access.

Client type

Whether the app can keep a secret. One that cannot, such as an app in a browser, has to rely on PKCE.

How the provider learns about the app

Someone registers it by hand, it registers itself, or it points at a document about itself. It changes the setup, and with a document the login too.

The app proves it started this login, so a stolen code is no use alone. Current advice is to have it on, and a public client must.

Drawn so far with nothing else on but OpenID Connect, consent and PKCE, with either kind of client and the app on a server.

The app sends its request straight to the identity provider, and the browser carries only the client ID and a reference.

The attacker only shows the plain case, with a Bearer token and no other provider.

Someone gets hold of the code and tries to use it. Flip PKCE, the client type or how they get it to see what changes.

Token type

Whether holding the token is enough, or the app must also prove it holds a key.

The IdP hands the login to another IdP. The app does not notice.

The identity provider checks users in LDAP or Active Directory.

Users log in at their own company, which the identity provider finds from their email.

Stored upstream tokens

The IdP keeps the upstream IdP's tokens, and the app can ask for them.

What the API is sent

The same call to the API, and what it answers depending on the token.

The API needs a second API to answer, and trades the token it got for one meant for that API.

What the trade gives back

Only a token for the second API, or a refresh token as well, so that the API can get another later without the user.

Drawn so far only on the plain flow, for an app with a secret and nothing else on.

Logged in, the user links an account at another provider, whose tokens the identity provider can keep.

Later on the access token expires, and the app gets a new one without the user.

A second app, the same identity provider, and no password.

Part of OpenID Connect.

The user logs out, and what ends is not everything.

Where the app runs

On a server of its own, in the page in the user’s browser, alone or with a server behind it, or in a program on the user’s computer. In the page alone there is nowhere to keep a secret, and in a program a secret shipped in every copy is no secret.

Which spec says so?

In Keycloak: Client scopes

The first API’s client has a client scope with an Audience mapper that names the second API, as a default scope. Without it, asking for that audience gets a 400 and: Requested audience not available: demo-api-two. With it, the new token names the second API, and not the first.
