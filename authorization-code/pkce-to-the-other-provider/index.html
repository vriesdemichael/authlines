What if the other provider hands the login on again?

Then the login passes through two providers after the identity provider: the other provider is a client in turn, of a provider behind it, the way the identity provider is here. The identity provider is a client only of the other provider. It never talks to the one behind and is not registered there, so all it knows is what the other provider tells it, and a it keeps from this login is the other provider’s. Nothing recorded here has a provider behind the other one, so this is drawn as one hop, and each further hop would be this same exchange again.

What it carries

  • response_type=code query Asks for a code, which is what makes this the code flow.
  • client_id query The identity provider's own client ID at the upstream
  • redirect_uri query The identity provider's broker endpoint
  • state query A random value the app checks when the user comes back, so nobody can slip an answer into this user's login. It does not stop someone starting a login in their own browser and handing the app a stolen code, which takes PKCE or a nonce.
  • scope=openid query What the identity provider is set up to ask this provider for. Here the app’s own scope did not go on
  • nonce query A random value that comes back inside the ID token, so the app can tell the token is from this login.
  • code_challenge query The identity provider’s own, for this leg From: PKCE to the other provider
  • code_challenge_method=S256 query How it was made: a one-way hash From: PKCE to the other provider
